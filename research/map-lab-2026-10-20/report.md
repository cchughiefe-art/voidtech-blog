# MAP communication-address prototype test

- Environment: Node v24.19.0, npm 11.9.0, mailschema 0.3.2. Installed with `npm install --ignore-scripts --no-audit --no-fund mailschema@0.3.2`. This run used the package CLI locally; no email was sent and no confirmation endpoint was implemented.
- I designed a repair-notes subscription confirmation fixture for my VOID site: one requested mailbox, one request identifier and a 30-minute window. The reserved `.example` mailbox is synthetic. The human URL describes a proposed route, not a deployed feature. There is no login authority or executable capability in this fixture.
- Downloaded the contract with `curl -fsSL --max-time 20 https://mailschema.org/artifacts/map-0.3/contracts/email-address-confirmation-0.1.json -o contract.json`. Ran `npx --no-install mailschema description description.json --contract contract.json`. Output: `Valid MAP 0.3 description urn:void:map-lab:20261020:reader-confirmation:001`, then `sha-256:db2ce23ff1aee04271ee9c1267deaf239156fefae16d09e93e521fc64fd2cf99`.
- Installation completed around 13:53 Lagos; first valid description around 15:51: approximately 118 wall-clock minutes, including a long pause for account verification and other work. This is not an estimate of uninterrupted implementation time. The slowest part was resolving account verification separately from validation.
- Negative test: changed `details.purpose` to `account-login`; ran the same CLI command. Its exact validation error was `/details/purpose: must be "communication-address"`. Restored `communication-address` and validated again.
- No package defect found in these checks. Checked the README at https://unpkg.com/mailschema@0.3.2/README.md and https://mailschema.org/registry/email-address-confirmation against the contract, positive run and negative run. Shape validation does not prove independent initiation context or live service behavior.
